# Vector Index (HNSW)

Read `.claude/docs/design/phase-0-transaction-and-format-spec.md` §4 and §6 for the exact conflict-domain and manifest-format definitions this crate must implement against — the bullets below are guardrails, not a substitute.

- **The index is a set of immutable, self-contained segments — one per committing transaction — never a shared graph mutated in place.** A commit builds its segment outside the commit lock, fsyncs it, and publishes it by the same atomic manifest swap that publishes its rows; a snapshot's segment set is exactly its manifest's `segments` list. That is what lets index changes commit atomically alongside row data instead of being patched in separately after the fact. Don't reintroduce a shared mutable graph, or any "apply now, persist later" path, for a "quick" performance fix without a design discussion first. (This replaced an append-only delta log in S1 W3.2 — see `docs/superpowers/specs/2026-07-24-s1-segment-format-w3-migration-design.md` §0.2 and §1. The log's only job was reconstructing a graph that was never persisted; a segment *is* the persisted graph.)
- **Segments are immutable and never rewritten.** Deletion is the manifest's versioned tombstone set applied through the traversal filter, not a per-node flag and not a segment rewrite: a row committed in segment 3 and deleted at version 12 stays physically in segment 3 forever, and a snapshot at v11 must still see it.
- The index lives inside the same transaction boundary as row data — it is not an eventually-consistent side structure. Any code path that updates the index outside `crates/txn/`'s commit path is a bug.
- HNSW parameters (`max_nb_connection`, `ef_construction`, `ef_search`) are tuned via benchmarks (`bench/`), not guessed — cite the benchmark run when changing a default.
- **`HnswIndex::insert_batch_parallel` had a real, measured clustered-data recall hazard, now fixed and verified end to end — and is gated behind `crates/txn`'s `parallel-insert` Cargo feature, off by default.** `crates/txn/src/dataset.rs`'s `build_and_write_segment` only calls it when that feature is enabled (`cargo build`/`cargo test -p strata-txn --features parallel-insert`); otherwise every commit's segment build uses a plain sequential per-row loop instead, matching `insert_batch_parallel`'s own small-batch fallback. This is defense-in-depth on top of the fix below, not a substitute for it — flip the feature on deliberately, don't treat "off by default" as license to skip re-verifying this hazard if the code around it changes. Found through the real `crates/txn` commit path (`a_large_single_commit_builds_a_correct_segment_and_every_row_is_visible`'s 200-row/20-cluster fixture, stress-tested under heavy concurrent CPU load): sequential insert consistently measures 0.00% failures; the original parallel path showed roughly 10-21% of commits losing at least one row (worst single-commit severity 21-24% of 200 rows). Because segments are immutable once sealed (see the first bullet above), a row that lost its only path from the entry point this way was **permanently** unfindable via `vector_search` — no later repair pass.
  - **The actual dominant mechanism (found after two other hypotheses were investigated and ruled out): a node is visible in `NodeTable` — and so findable as a search candidate — from the moment its slot is claimed, well before its own edges at every layer are built.** A concurrent insert's own descent can pick that not-yet-finished node as its nearest candidate and carry it down as the ENTRY into the next-lower layer; `search_layer` seeded there returns nothing but that one node, so the concurrent insert's own candidate set collapses to 1 and it ends up with a handful of edges instead of dozens. Fixed by `Node::is_published`/`mark_published` (`crates/index/src/node.rs`) and a publication guard on both of `Graph::insert`'s descent loops (`crates/index/src/graph.rs`) — a node is marked published only once its own connection-building finishes, and a concurrent descent now picks the nearest PUBLISHED candidate as its next entry, keeping the current entry if none qualify. Deliberately NOT applied to ordinary candidate/connection selection (a not-yet-published node is still a perfectly good neighbor to connect TO — excluding it from that path was measured to make the hazard WORSE).
  - **Verified end to end: 0/800 real commits of the same 200-row/20-cluster fixture, through the actual commit path, under the same heavy concurrent load that produced the original 10-21% failure rate, lost a single row.** Full parity with sequential insert's own 0.00% — not a bounded mitigation, the hazard is closed. Also proven at the unit level by a dedicated, exhaustive `loom` model (`concurrent_insert_never_uses_an_unpublished_node_as_a_descent_entry_loom` in `graph.rs`'s `loom_tests`) that deterministically reproduces the candidate-set collapse when the publication guard is ablated, and passes cleanly with it in place. See `Graph::insert`'s own doc comment in `graph.rs` for the complete mechanism writeup, the two hypotheses that were investigated and ruled out as the DOMINANT mechanism (physical claim-slot exhaustion; stale-decision compounding in the neighbor-shrink step — both real in principle, neither was actually firing at production parameters, per direct instrumentation), and all the numbers. Ruled-out-as-dominant is not the same as removed: the claim-slot-exhaustion fix was reverted as dead code (unreachable at production parameters), but the shrink-step retry-loop fix was KEPT and ships today, as a correctness guard for a hazard that's real in principle even though it wasn't the one causing the measured failure rate. That retry loop is itself now bounded (`run_shrink_retry_loop` in `graph.rs`, `MAX_SHRINK_RETRIES = 64`) — a theoretical-unbounded-stall risk on the commit path, closed by reporting `IndexError::NeighborShrinkDidNotConverge` instead of looping forever or silently leaving a neighbor over capacity if the bound is ever hit (believed unreachable in practice; see that function's own doc comment).
  - **A separate, more severe bug was found and fixed independently: the empty-graph race.** Two threads racing to insert into a genuinely empty graph could both take the zero-connections fast path and only one would win the entry-point race, permanently stranding the other. Not clustered-data-specific — any two concurrent `Graph::insert` calls on a fresh graph could hit it. Fixed by `EntryPoint::claim_if_empty` (makes "am I first" a single atomic claim) and proven by a small exhaustive `loom` model (`concurrent_inserts_into_a_genuinely_empty_graph_never_strand_a_node_loom` in `graph.rs`'s `loom_tests`) that deterministically reproduces the strand pre-fix and passes cleanly post-fix.
  - **`HnswIndex::insert_batch_parallel`'s chunking (`crates/index/src/hnsw.rs`) is round-robin, not contiguous.** Row `i` is assigned to `chunks[i % num_chunks]`, not to a contiguous block — chunk sizes are unchanged (still `base` or `base + 1` rows), only membership changed. Rows arrive from `crates/txn` in whatever order a commit's own writes came in, which for topic-clustered embeddings tends to group same-cluster rows together; contiguous chunking would then hand one whole cluster to one worker, maximizing exactly the half-built-neighborhood exposure hazard #4 above exploits (each worker's own region built against a graph missing every other region for as long as its siblings are still inserting theirs). This is defense-in-depth alongside the publication-barrier fix, not a replacement for it.
  - **The publication guard is a write-path-only fix — `crates/index/src/graph.rs`'s `k_nn_search_generic` (the read path behind `HnswIndex::search`) has no equivalent guard on its own layer-descent loop, and that's a deliberate scope cut, not an oversight.** `HnswIndex::search`/`insert` are both `pub`, so a caller outside `crates/txn` *could* run them concurrently on the same instance, but Strata's own production caller never does — a per-commit `Graph` is exclusively under construction until sealed into an immutable segment, never handed to a reader before then (see the first bullet above). A reader racing an unpublished node only costs a transient, self-healing recall dip, unlike a writer racing one, which bakes a permanent connectivity loss into the graph — not worth guarding a hot read path against a precondition production never creates. See that function's own doc comment if a future caller ever needs concurrent search-during-insert.
  - `bench/benches/vector_search_bench.rs` is the dedicated recall-at-realistic-scale benchmark (100K real embeddings) and asserts a recall@10 floor of 0.8 — kept as the production-scale recall gate; it doesn't specifically exercise clustered-topology construction races, which is what the 200-row/20-cluster fixture and the fixes above are for.
  - `tests/sim/tests/chaos.rs`'s invariant 4 asserts *strict* per-row findability after every commit. With the fixes above this should now hold even for a future multi-row-per-commit chaos workload (today's chaos-worker commits 1 row per transaction, so this was never actually exercised there) — but don't assume that without adding coverage once such a workload exists; re-verify rather than trust this note going stale.
- `crates/index` is a from-scratch, fully lock-free HNSW implementation — it no longer depends on `hnsw_rs` (or `usearch`'s Rust bindings, or any other external ANN library). Full replacement was justified narrowly by a lock-free-concurrent-mutation requirement that no wrap/fork of an existing library could satisfy — see `docs/superpowers/specs/2026-07-18-hnsw-rs-wrap-vs-replace-decision.md` and `docs/superpowers/specs/2026-07-18-lockfree-hnsw-rewrite-design.md`. The only remaining external dependency is `anndists` (`simdeez_f` feature enabled), used narrowly for SIMD distance kernels — not for graph structure, traversal, or concurrency, all of which are this project's own code. **No HNSW library audited, in C++ or Rust, exposes graph internals for the segment serialization Strata's own on-disk format needs** — that codec (`crates/index/src/segment_{format,writer,reader}.rs`) is entirely Strata's own code regardless of backing implementation.
- IVF-PQ and other index types are an explicit non-goal for v1 — don't add a second index type without checking the Non-Goals table in `.claude/docs/architecture.md` first.
